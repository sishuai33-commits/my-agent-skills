## 一、第一性原则（画图前先读这五条）

### 1. 图即地图，必须自描述（Simon Brown，C4 创造者）

- **抽象集 > 符号集**。团队图乱，根因不是符号不统一，是没有共同的抽象层。
- 图要像地图自描述：**标题（图类型+范围）+ 图例是必备件，不是装饰品**。
- 受众分层：画图前先定给谁看。给错层级的受众 = 没有图。

### 2. 阅读密度：概览优先少量核心概念

- 抽象不是省墨，是把多个元素打包成一个 chunk。概览可先尝试 5–9 个核心概念，按阅读效果拆图或下沉细节。这是布局经验，不是由记忆研究直接推出的节点硬上限。
- 术语一致、符号一致本身就是减负（schema 压缩信息量）。
- 冗余效应：图和文字重复表达同一信息反而增负。**图说结构，文字说决策。**

### 3. 一图一层次、一图一受众（C4 + Kruchten 4+1）

- C4 第一铁律：**Never mix levels**。同类节点使用一致的抽象口径；上下文外部系统与内部展开、明确的跨视图映射须标出类型和边界，不能混作同类节点。
- 判据：如果你需要在图上加一句"这个框其实是个高层概念"来解释，这张图就混层了。
- Kruchten 4+1：**每个视图服务特定干系人的特定关切**。没有"一张总图"。

### 4. 守恒与平衡（DFD Balancing，Yourdon/DeMarco）

- 父图某过程的输入输出 ≡ 子图边界的输入输出，**不多不少**。
- 改任何一层发现新数据流 → 必须回头改父图。这是所有分层图的通用校验手段。

### 5. 图即代码（Diagram as Code）

- 文本源（HTML/SVG/DSL）进版本控制、可 diff；白板截图和 PNG 是死资产。
- 活文档纪律：图不更新就是负资产。维护底稿与当前有效图的一致性；局部修改保留已认可布局，结构变化再重画。未更新的图明确标为待更新。

## 二、通用反模式清单（12 个已命名的坑，画图前对照）

| # | 反模式 | 症状 | 解法 | 来源 |
|---|--------|------|------|------|
| 1 | **God Diagram** | 一张图想表达一切 | 拆成多张、按抽象层级分层 | InfraSketch |
| 2 | **Boxes & Lines Soup** | 随机方框+交叉线，无组织 | 布局承载语义：分组、对齐、流向一致 | InfraSketch |
| 3 | **Technology Worship** | 堆满框架/库/工具名 | 主图只画逻辑组件，技术细节放实现文档 | InfraSketch |
| 4 | **Missing Context** | 不画外部依赖 | 上下文不清时先澄清边界，已有上下文则复用 | InfraSketch |
| 5 | **Inconsistent Notation** | 颜色/形状/线型随机用 | 每图必带图例 | IcePanel |
| 6 | **Unlabeled Lines** | "这很明显"的连线 | 交互线标含义与方向，协议仅在已知且适用时标注 | IcePanel |
| 7 | **Mixed Abstractions** | 低层模块直连高层抽象 | 分层；跨视图映射须标类型/边界，不用一句免责说明掩盖混层 | IcePanel |
| 8 | **Unconnected Resource** | 孤立节点 | 关系图检查遗漏；包含关系和静态目录无需强加连线 | Ilograph |

| 11 | **装饰性动画/彩虹色** | 营销图风格 | 技术图颜色 ≤3-4 种且有语义 | Ilograph |
| 12 | **Stingy Labels** | 新手极度吝啬标注 | activity 全标注 verb-noun、网关出边全标注、终态全标注 | Bruce Silver |

## 三、选图：4A 视图 × 图类型矩阵

| 4A 面 | 回答的问题 | 推荐图类型 | 关键元素 |
|-------|-----------|-----------|---------|
| **BA** | 为谁创造什么价值？怎么做？ | 价值流图、能力地图、流程泳道图、业务对象关系图 | 价值流/阶段/能力/流程/对象/干系人 |
| **IA** | 数据长什么样？怎么组织流转？ | 数据资产目录树、ER 图、数据流图(DFD) | 主题域/业务对象/实体/属性/数据源 |
| **AA** | 系统怎么组织？怎么调用？ | C4 容器/组件图、应用组件图、服务调用时序图 | 系统/模块/服务/接口/调用链 |
| **TA** | 技术怎么支撑？部署在哪？ | 部署拓扑图、技术栈分层图、选型对比图 | 技术域/组件/部署节点/信任边界 |

**视角对偶**：能力地图 = 业务"静态"视图（at rest），价值流/流程 = "动态"视图（in motion）。需要同时讨论静态职责和动态流转时分别表达，不默认每次都出两张。

**受众 × 颗粒度**（一稿多投，不维护多份内容）：

| 受众 | 给什么 | 颗粒度 |
|---|---|---|
| 领导/业务 | 价值流图、能力地图 | L1-L2，业务语言 |
| 客户技术 | 组件图、集成关系图 | L3，模块+接口 |
| 实施 | 部署拓扑、数据流图 | L4-L5，字段+协议 |

## 四、BA 图规则

### 4.1 价值流图

- 水平从左到右：触发 → 阶段 → 完成；阶段用圆角矩形，标触发条件(Entrance)/退出条件(Exit)/价值增量
- 干系人在左侧；价值流不止一条时上下分层
- **不画活动/任务级细节**（那是流程图的事）

### 4.2 能力地图（SAP LeanIX 规则精选）

1. **MECE 不重叠**；说 what 不说 how（能力 ≠ 流程）
2. **长期稳定**：组织变，能力不变
3. 顶层 7-10 个能力，一般不超过 3 层
4. 热力图着色：绿=充分 / 黄=部分 / 红=缺失
5. **能力之间不画箭头**（静态目录，不是流程）

### 4.3 流程图（泳道/活动图）——BPMN Method & Style 标注铁律（Bruce Silver）

1. **所有 activity 用 verb-noun 命名**，同过程内不重名
2. **排他网关的每条出边必须标注条件**
3. 结束事件标注终态（成功/失败/取消——多终态必须区分）
4. 实施流程应覆盖影响结果的异常；概览可标异常去向并在详图展开
5. **跨泳道线 = 交接点**，沟通失败高发区，重点标注
6. "Complete information"自检：只看图能否一眼说出——流程如何开始、实例是什么、所有可能终态、所有路径、所有外部交互？
7. 决策逻辑别嵌成 gateway 链 → 复杂判断拆决策表（DMN 思想）

### 4.4 ER / 业务对象关系图——Crow's Foot 记号（Gordon Everest）

| 端点符号 | 含义 |
|---------|------|
| 圈+竖线 | 零或一（可选） |
| 竖线+竖线 | 恰好一（必选） |
| 圈+鸡爪 | 零或多 |
| 竖线+鸡爪 | 一或多 |

- 两个符号组合读：**外侧=基数(max)，内侧=可选性(min)**
- 实体名单数；主键加粗/下划线；关系线标角色名（双向可读）
- 相关对象靠近，避免交叉线；业务对象分组用背景框

## 五、IA 图规则

### 5.1 数据资产目录树

- L1-L5 层级：主题域分组 → 主题域 → 业务对象 → 逻辑实体 → 属性
- **L3 业务对象是视觉重点**（加粗/底色）；标注数据 Owner 和主数据源

### 5.2 数据流图（DFD）——Yourdon 权威规则

**四条结构规则**（违反 = 图画错，不是风格问题）：

- 每个过程至少一个输入、一个输出（**有进无出 = 黑洞，有出无进 = 奇迹**）
- 检查存储的读写来源和去向；局部图可只显示范围内读或写，不为凑双向箭头编造数据流，相关另一侧在说明或关联视图交代
- 数据不直接从外部实体到存储，必须经过过程
- 过程可以与外部实体、其他过程或存储交换数据；禁止外部实体/存储之间绕过过程直接相连。参见 [Visual Paradigm 连接规则](https://www.visual-paradigm.com/support/documents/vpuserguide/1284/992/36119_dataflowdiag.html)

**分层与编号**：

| 层级 | 编号 | 关注点 | 该画 | 不该画 |
|------|------|--------|------|--------|
| Context | 过程 0 | 系统与外部交互 | 系统=1个泡 + 外部实体 + 主数据流 | 内部过程、存储 |
| L0 | 1, 2, 3... | 系统内部全貌 | 少量核心过程、关键存储、主干流 | 详细活动、异常分支 |
| L1 | 2.1, 2.2... | 单过程展开 | 子过程、局部存储、判定、回灌 | 其他过程的内部 |
| L2 | 2.3.1... | 更深细节 | 一般到 L2 为止 | — |

**硬规则**：
- **Balancing**：父过程输入输出 ≡ 子图边界，发现新流 → 同时改两层
- **Local store**：只被某层内部使用的存储，只画在该层，不上浮父图
- **命名守恒**：同一存储/流跨层名字必须一致

**概览画法建议**（以本项目 Context/L0/L1 定义为准，不混用层级编号）：一图一层次，细节下沉 L2；先定 3-7 个核心过程再挂存储；外部实体按上/左/右分散放；主干横平竖直少斜线；反馈/回灌合并为一条（L2 再展开）；质量监督可用文字标注框。

## 六、AA 图规则

### 6.1 C4（Simon Brown）——每层回答一个问题、面向一个受众

| C4 层级 | 回答 | 受众 | 经济性 |
|--------|------|------|--------|
| C1 系统上下文 | 系统是什么？谁用？依赖什么外部系统？ | 所有人（含非技术） | **几乎总是值得画** |
| C2 容器 | 由哪些应用/数据库/服务组成？技术选型？ | 技术人员 | **几乎总是值得画** |
| C3 组件 | 单个容器内部怎么组织？ | 该容器开发团队 | 只给复杂容器画 |
| C4 代码 | 组件怎么映射到类/接口？ | 开发者 | **不手画**，工具生成 |

**铁律**：
1. **Never mix levels**
2. 上下文未对齐时先澄清；已有上下文可直接进入所需层级
3. 反模式：Context 图画 30 个外部系统 = 藏起内部的 Container 图（混层伪装）
4. 标题格式：「图类型 + for + 范围」；符号自定义但**必须配图例**
5. 逆向现状组件应映射代码库真实抽象；目标设计组件标为建议/已决定，不能假称已经实现

### 6.2 时序图

- 参与者按调用顺序从左到右；时间自上而下
- 同步消息=实线实心箭头；异步消息=实线开口箭头；返回=虚线。置信度另用文字标记，避免线型歧义
- 分支/循环用 alt/opt/loop 框；消息编号（1, 1.1, 1.2）表达嵌套

## 七、TA 图规则

### 7.1 部署拓扑图

- **网络区域/信任边界必须显式**（虚线框：内网/DMZ/公网）
- 组件实例画在部署节点上；连线标已知且当前层级需要的协议/端口，未知不臆造
- 颜色只为边界/关键路径服务；细节深度随受众调

### 7.2 技术栈分层图

- 表现层 → 应用层 → 服务层 → 数据层 → 基础设施，严格分层
- 同层横向排列；跨层调用箭头方向一致

### 7.3 技术选型对比图

- 候选方案为列、评估维度为行、评分为绿黄红或 ★

## 九、4A 语义色约定（多图一致性）

同一项目多张图保持领域语义一致：

| 语义 | 色系 |
|---|---|
| BA 业务/价值流 | 蓝 |
| IA 数据/对象 | 灰 |
| AA 应用/消费 | 橙 |
| TA 技术/基础设施 | 靛青 |
| 风险/缺口/待确认 | 红（待确认再加问号） |
| 推断内容 | 优先文字标“推断/建议”；线型不得与当前图种语义冲突 |
| 人/干系人 | 黄 |

具体色值随交付轨道而定：走汇报生图/PPT 主轨时遵循目标客户/企业风格（如华为白底红灰），用位置、分区和克制重点色区分层次；走 HTML 副轨时按 `diagram-handoff.md` 的柔和浅色 token 取近似色。**色盲冗余**：不只用颜色，同时用形状/线型/标签区分。

## 十、质量检查清单

**A 组不过 = 返工，不交付。** 视觉细节的生产规范以 diagram-design §9 taste gate 为准，本清单侧重架构判断验收。

### A 组：通用（C4 官方，c4model.com/diagrams/checklist）

- [ ] 图有标题吗？（含图类型+范围，如 "Container diagram for X"）
- [ ] 看图的人能明白图的类型和范围吗？有图例吗？
- [ ] 每个元素都有名字吗？抽象层级类型能看明白吗？是干什么的能看明白吗？
- [ ] 所有缩写、颜色、形状、边框样式的含义都明确吗？
- [ ] **每个箭头都有标注吗？**标注和方向一致吗？关系的技术选择（协议等）在适用处标明了吗？

### B 组：抽象与密度

- [ ] 同类节点抽象口径一致？跨视图映射是否标明类型/边界？
- [ ] 概览能抓住主干？拥挤时是否分区、拆图或下沉，且未删除关键关系？
- [ ] 关系图无不明孤立节点？静态目录与包含关系不要求每个节点一条连线
- [ ] 分层图满足 Balancing（父子图输入输出守恒）？
- [ ] 同名元素跨图命名一致？

### C 组：验收抽查

- [ ] 去掉所有文字后，结构是否仍能传达概念？
- [ ] 流向一致（左→右或上→下），逆向线有箭头？
- [ ] 不只用颜色编码（色盲冗余：形状/线型/标签）？
- [ ] 文字无截断？

### D 组：4A 专项

- [ ] 现状/目标、事实/建议/待确认是否可辨？状态标记是否与异步/返回/边界线型冲突？
- [ ] BA：标注了触发/价值增量/参与者？能力图无箭头（静态目录）？
- [ ] 流程：异常分支画了吗？网关出边全标注？终态区分？跨泳道交接点标注？
- [ ] IA/DFD：无黑洞（有进无出）？存储的读写去向可解释（局部视图未画的另一侧有交代）？标注数据来源/Owner？
- [ ] ER：基数符号齐全？主键标识？
- [ ] AA：接口/协议是否在已知且当前层级需要时标注，未知项是否明确保留待确认？现状组件有实现依据，目标组件未冒充已实现？
- [ ] TA：标注技术选型/部署节点/信任边界？

### E 组：成套叙事与汇报页审稿（多页图定稿 / 转 PPT 前必查）

- [ ] 每页是否只有一句清晰主结论，成套连读顺畅无断层或重复页？
- [ ] 后页展开的每个模块，能否精准指回总览页对应框，名称与归属无漂移？
- [ ] 客观事实、理想故事包装、本期承诺红线是否可辨，无越界承诺？
- [ ] 汇报生图是否逐字复核中文错字、多余装饰/logo 及为凑闭环编造的接收方？
