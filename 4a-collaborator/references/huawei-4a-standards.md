## 一、4A "一体四面"总览

华为 4A = CSG-EAF 2.0 企业架构框架，融合 TOGAF + DDD + 基于职能的业务能力分析 + 基于价值的端到端流程分析。

- **一体**：瞄准业务目标/问题，架构师团队协同设计
- **四面**：业务架构 BA / 信息架构 IA / 应用架构 AA / 技术架构 TA，一个都不能少

四层关系：自上而下决定（战略→业务→技术），自下而上支撑（技术→业务→战略）。BA 是起点，IA/AA 承上启下，TA 兜底。

### 命名坑（重要，别踩）
1. **IA vs DA**：华为官方叫"信息架构 IA"，刻意不叫"数据架构 DA"。原因是华为用"信息"强调业务对象的语义层（产品/客户/合同/订单/员工的数字镜像），不只是数据库表。二手资料常混用 DA/IA，看材料时要分清说的是哪一层。
2. **"一体四面"笔误**：网上流传版有把四面写成"业务架构、信息架构、应用架构、信息架构、技术架构"（信息架构重复），是笔误。官方四面不重复。

## 二、EA 元模型 L 层级表（材料归类标尺 + 咬合校验骨架）

华为把 4A 每层都标准化成 L1-L5 分层。这是识别输入材料归属、做层间咬合校验的硬骨架。

| 架构域 | L1 | L2 | L3 | L4 | L5 |
|---|---|---|---|---|---|
| BA-价值流 | 价值流 | 价值流阶段 | — | — | — |
| BA-业务能力 | 能力类 | 能力组 | 业务能力 | 业务服务 | — |
| BA-流程架构 | 流程类 | 流程组 | 流程 | 活动 | 任务 |
| IA | 主题域分组 | 主题域 | 业务对象 | 逻辑数据实体 | 属性 |
| AA | 产品族 | 产品 | 应用系统模块 | 应用服务 | 物理应用组件 |
| TA | 技术域 | 技术子域 | 技术服务/组件 | — | — |

用法：
- **提取归位**：喂入一段材料，按其颗粒度归到具体 L 层（如"客户下单流程"→ BA-流程架构 L3 流程）
- **查漏补缺**：检查层间映射是否成立（见下"元模型三类关系"）

## 三、Y 模型（华为 BA 设计核心方法 → 正向设计推荐逻辑链）

```
价值流 (为什么做)  ──┐
                    ├──→ 收敛 ──→ 业务流程 (怎么做)
业务能力 (做什么) ──┘
```

- **价值流**：端到端活动集合，为客户创造价值。从客户视角出发，逼问"这步创造什么价值"
- **业务能力**：企业拥有/获取的特定能力，用于实现特定目的
- **业务流程**：承载价值流与业务能力

推荐链（提取归位/讨论时用）：
```
客户痛点/旅程 → 价值流阶段 → 业务能力断点 → 业务对象
```
即：把"客户痛点（症状）"追因到"能力断点（根因：哪个能力缺失/不足导致）"，再映射到需数字化的"业务对象"。

⚠️ 关键转变：华为 BA 要求从**职能管控视角**转向**客户视角/价值创造视角**。
- "业务流"（内部：谁做什么、什么顺序）≠ "价值流"（外部：为谁创造什么价值）
- 只收集痛点 → BA 变需求清单/吐槽墙；痛点→能力断点→能力重构 → BA 才是架构设计

## 四、元模型三类关系（层间咬合校验分类）

| 关系类型 | 含义 | 校验示例 |
|---|---|---|
| 依赖 (Dependencies) | 某元素依赖特定元素 | 某应用依赖特定技术栈/服务 |
| 支持 (Support) | 某元素支持多个元素 | 某技术为多个应用提供支持 |
| 实现 (Implementation) | 某元素实现特定元素 | 某应用实现某业务能力/流程 |

核心咬合校验矩阵（查漏补缺必查）：
- BA 业务对象 ↔ IA 数据模型（每个业务对象都有数据模型承载？）
- BA 业务能力 ↔ AA 应用（每个能力都有应用承载？）
- BA 价值流 ↔ AA 端到端协同（价值流在应用层跑得通？）
- AA 应用 ↔ TA 技术组件（每个应用都有技术支撑？）

## 五、IA 五要素（IA 单层完整性清单）

数据架构/信息架构梳理需确定五要素：
1. **数据 Owner**：每个业务对象任命唯一 Owner，制定管理规则，负责数据质量
2. **数据源**：数据从哪来
3. **数据分类**：L1 主题域分组 / L2 主题域 / L3 业务对象 ...
4. **数据分级**：敏感度/安全级别
5. **数据标准**：属性层数据含义与业务规则

IA 四组件：数据资产目录 / 数据标准 / 企业级数据模型 / 数据分布

## 六、业务对象四原则（识别业务对象的判定标准）

业务对象是 IA 最核心管理要素——企业重要的人、事、物、地，承载业务运作和管理信息。识别时遵循四原则：

1. **重要性**：企业运作管理中不可缺少，通常有相应管理流程/组织/IT系统支撑，需任命唯一数据 Owner
2. **唯一性**：有唯一身份标识（实例化编码），企业范围内唯一
3. **稳定性**：至真至实反映业务，相对稳定，与组织和流程解耦，企业内唯一且只归属唯一主题域
4. **可实例化**：可实例化，对应建模语言中的概念实体

向下分解：业务对象 → 逻辑数据实体 → 属性。
例：销售订单（业务对象）→ 销售订单头/行（逻辑实体）→ 订单编码/单价/数量（属性）

## 八、华为流程分层 L1-L6（BA 流程架构深化时参考）

- L1 流程分类 / L2 流程组：WHY TO DO，支撑战略，集团级主干
- L3 流程 / L4 子流程：WHAT TO DO，创造客户价值的主业务流
- L5 活动 / L6 任务：HOW TO DO，落实到角色可执行

流程三类：执行类（LTC/IPD/MTL/ITR，直接面向客户）/ 使能类（供应链/采购/技术开发）/ 支撑类（HR/财经/IT）

原则：主干清晰，末端灵活。主干流程集团定，末端流程区域定。

## 九、与 TOGAF / DDD 的关系

- 4A 脱胎于 TOGAF（TOGAF 四大架构域：业务/数据/应用/技术）
- 华为融合 DDD：BA 的能力/流程可映射到 DDD 领域模型与限界上下文；AA 的应用划分契合 DDD 限界上下文与聚合；IA 的业务对象对应 DDD 领域实体
- 与 TOGAF 区别：TOGAF 里数据架构与应用架构合并为"信息系统架构"，华为独立提 IA 反映"数据驱动"转向

## 十、V模型完整链条

价值流(创造什么价值) → 业务能力(场景形态) → 业务场景(5W1H) → 业务流程(承载价值流+能力) → 业务活动(输入输出=表/证/单/书) → 业务对象(4特征) → 应用服务(封装业务对象操作) → 应用系统模块 → 产品 → 产品族

**V模型核心**：围绕相对稳定的业务对象设计业务和IT——不管组织/流程/场景怎么变，业务对象稳定。

## 十一、TOGAF官方价值流4要素6阶段（The Open Group官方）

### 价值流4要素
1. Name（动宾结构，如"Acquire Retail Product"）
2. Description（范围说明）
3. Stakeholder（触发者）
4. Value（stakeholder期望获得的价值）

### 价值流阶段6要素
1. Name 2. Description 3. Stakeholders 4. Entrance Criteria 5. Exit Criteria 6. Value Item

### 价值流vs业务流程
- 价值流：outside-in视角（客户/终端用户）
- 业务流程：inside-out视角（运营层面）
- 价值流阶段→业务流程**不是一对一映射**

## 十二、一体四面协同

```
BA(业务架构) ← 锚点
  ↓ 数据从业务域派生
IA(信息架构) ← 业务对象是BA到IA的桥梁
  ↓ 能力从业务能力拆分
AA(应用架构) ← 应用服务实现业务能力
  ↓ 运行需求从业务场景导出
TA(技术架构) ← 技术底座支撑应用/数据/业务
```

可追溯：能力→服务→数据实体→技术平台

## 十三、三层数字化

- **对象数字化(What)**：物理实体→数字对象，全要素可感知（唯一ID+属性+状态）
- **过程数字化(How)**：业务活动在线化，端到端可视可溯可优化
- **规则数字化(Why)**：业务规则→算法模型，智能决策，变"人治"为"数治"

## 十八、变形适配（何时裁剪）

基于批判性反思，执行时按项目规模裁剪：

- **TOGAF vs DDD 张力**：高阶架构稳定治理，子系统开放给 DDD——对应量子"对外包装稳定+对内实际灵活"
- **一体四面成本**：小团队不必全追溯，按规模裁剪追溯深度
- **V模型局限**：对持续交付支持不足，扩展为多层验证闭环
- **Y模型素养要求**：小团队过度工程化风险，按规模简化 Y
