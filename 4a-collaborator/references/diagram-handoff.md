## 交接内容

从当前项目底稿和讨论形成以下信息，可内联在工作上下文，不必另造表单，也不要求用户逐项确认：

- 这张图帮助谁判断什么；范围、现状/目标、成熟度（草案/已讨论决定）。
- 图种和抽象层；节点的稳定名称、职责、边界/包含关系。
- 每条关键关系的起点、终点、方向、含义；数据流标数据、调用标动作，协议仅在已知且适用时出现。
- 未决点与依据；需要保留的既有决定，以及这次明确下沉到详图的内容。
- 交付文件位置和当前有效版本；已有图则提供源文件及本轮变更范围。

没有唯一方案时，允许画有清楚条件的方案草图；不要用精美图面掩盖架构分歧。

## 两个技能之间的口径

- 架构内容、项目已决定事项和用户要求优先于绘图示例。不能为了节点数量预算删掉影响结论的责任、依赖或失败路径；优先概览+详图或旁注。
- 容器嵌套可以表达包含关系，静态能力图无需连线；调用/数据传递不能只靠摆放位置暗示。
- 不把置信度、异步消息、返回消息、信任边界全画成同一种虚线。优先用“建议/待确认”等文本标记表达状态；线型遵守当前图种语义，图例只解释实际出现的编码。
- 草图仍需正确的名称和关系；不要求尚未确定的目标组件映射到已存在代码。
- 使用技能中确实存在的 `scripts/self_check.py`。上游文档提到的 `verify-geometry.py` 等仓库脚本若未安装，不反复寻找、不声称已运行；用可用浏览器检查弥补，并说明未覆盖部分。

## 实际验收

1. 对照交接内容回读 HTML 中的节点和关系，检查遗漏、名称、方向及方案状态；改图时检查父子视图和相关说明。
2. 运行实际存在的 self-check，修复结构/无障碍/单文件检查错误；它不证明架构正确或排版合格。
3. 用可用浏览器/渲染工具打开文件，实际检查中文、长标签、图例、线与框、缩放后的阅读效果。检查画布是否裁切、连线是否能从起点追到终点；布局拥挤时回到抽象层级调整。
4. 修改后回看受影响区域。没有渲染能力时保留源码并说明“尚未完成视觉验证”；不能以 HTML 存在代替可读性验收。
5. 最终交付当前 HTML 的可点击链接和必要的设计结论/未决点。草图明确为草图，验证材料留在工作区。
