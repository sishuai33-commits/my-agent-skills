# code-quality.md — 代码质量审查 prompt 模板

对项目代码进行全面质量审查。按 P0/P1/P2 严重度分级，每个发现需带有文件名:行号 + 证据 + 验证命令。

## 审查维度

### 1. 错误处理
- 是否有 `except:pass` 吞错误？fail-open 声明但实际 fail-close？
- 未处理的边界条件（空输入/超时/网络异常）
- Shell 脚本：set -e 与 grep -q 交互陷阱、空变量致危险操作、pipefail

### 2. 死代码 / 僵尸代码
- 注释掉的代码块未删除
- 从不执行的路径（条件恒真/假）
- 已被替代但未删除的旧逻辑
- 已注册但生产环境 0 触发的 hook → **也属于架构维度（僵尸架构）**，标记后 Tier 3 架构审查会深度追查

### 3. 代码重复
- 两个以上文件中出现相同逻辑但未抽取共享模块
- Shell 和 Python 版本功能重叠（如 slow-loop-audit.sh vs .py）→ **也属于架构维度（技术栈冗余）**，标记后 Tier 3 架构审查会深度追查
- 同一函数/工具在多个文件中重复定义

### 4. 隐藏耦合
- 脚本 A 动态 import 脚本 B 的私有函数（非 CLI 子命令）
- 依赖另一个脚本的副作用（文件格式/环境变量）但未声明
- 路径硬编码到已归档停用的旧位置

### 5. 机制 vs 资产分离
- 机制层（hook/框架代码）是否硬编了资产层内容（个人阈值/项目名/专家名）？
- 可插拔配置是否已有消费方？无消费方的 "doc_only" 配置是否应降级？

### 6. 错误面检查
- 多脚本共用的相同逻辑（now_utc_iso / cursor 管理 / working memory 解析）
- Shell 脚本的跨平台兼容性（BSD vs GNU stat / md5 vs md5sum）
- 临时文件是否有 trap 清理？

## 输出格式

对每个发现：
```
[严重度] 文件:行号 — 问题描述
  证据: <具体代码片段或数据>
  建议: <修复方案>
  验证: <一行命令，exit 0 = 已修复>
```

按严重度排序：P0 → P1 → P2。最后给**结构性问题总结**（不超过 3 条系统性缺陷）。
