# architecture-review.md — 架构审查 prompt 模板

对抗性审查项目架构设计。核心问题：**概念地基自洽吗？架构图 vs 实现 gap 多大？**

本 prompt 对应六维评估框架的**架构**维度。**参考外部标准优先**——以 CC 官方插件最佳实践为标准，而非项目自己的范式文档。

## 审查维度

### 1. CC 插件最佳实践符合性

参照 CC 官方插件文档（superpowers `developing-claude-code-plugins` / `working-with-claude-code`），检查项目结构：

- hooks / skills / commands / agents 的使用是否恰当？
  - 能用 hook 解决的问题是否用了 skill？（skill 有启动成本，hook 是会话级）
  - skill 是否承载了过多"机制层"逻辑？（skill 应做交互入口，非后台机制）
  - agent 是否有明确职责边界，还是职责重叠/交叉调用？
  - commands 是否被滥用为"隐藏的脚本入口"？
- `CLAUDE.md` 是否被当作了架构决策记录（ADR），而非实际使用指南？
- 项目文件组织是否符合 CC 项目惯用结构（lib/ 放核心逻辑，hooks/ 放集成，scripts/ 放工具）？
- 是否存在 CC 官方不推荐的模式？

### 2. 内核与胶水分离

- **核心逻辑**是否在 `lib/` 中，**集成交互**是否在 `hooks/` 中？
- hook 是否承载了不该有的业务逻辑？（hook 应做"接线"，不做"计算"）
- 如果删除所有 hook 文件，核心机制是否还能独立存在和测试？
- 框架代码和资产代码的边界是否清晰？（个人阈值、项目名、专家名是否被硬编码进机制层？）
- 机制层是否可被其他项目复用？如果不能，耦合度多高？

### 3. 模块间数据流契约

- 谁写什么、谁读什么：有明确的契约文件吗？
- 数据格式变更时，消费方是否会被通知/断裂？
- 是否存在隐式的"接口"——靠文件名约定 + 文本解析的脆性连接？
- 跨模块依赖图中是否存在环状依赖？
- 模块间的通信方式是函数调用、文件共享、环境变量，还是三者混用？

### 4. 架构冗余

- 同一概念是否有多种实现方式？
  - Shell + Python 共存实现相同功能 → 技术栈冗余，维护成本翻倍
  - 多个脚本做同一件事但入口不同
- 已注册但生产环境 0 触发的 hook → **僵尸架构**
  - hooks.json 中有注册但 probe mtime 从未更新 / 日志中无触发记录
- 多个同方向但功能重叠的配置文件 → 配置膨胀
- 旧实现被替代后未清理 → 历史遗留膨胀

### 5. 参考外部标准

**优先级：外部官方标准 > 内部范式文档**

- CC 官方 hooks / skills / commands / agents 最佳实践（superpowers 文档体系）
- CC 项目惯用的 `lib/` vs `hooks/` vs `scripts/` vs `commands/` 目录结构
- 对比行业标准的 CC 插件架构，本项目是偏重（过度工程）还是不足（面条式）？
- 项目是否"重新发明了轮子"？CC 提供的原生能力（如 pre-tool-use hook, MCP server）是否被绕过不用？

### 6. 复杂度预算

- **文件总数、代码行数、编程语言数**是否在合理范围？
  - 增长趋势：最近 30 天新增多少文件/行数？与价值产出是否匹配？
- 是否存在"过度工程"或"抽象泄漏"？
  - 为"可扩展性"加了多层抽象，但实际只有一个消费方
  - 抽象层泄漏了底层细节（调用者需要了解内部实现才能使用）
- 每个模块的圈复杂度是否可控？是否存在"万金油"文件（承载了过多职责）？

### 7. 反馈闭环完整性

- 机制闭环是否真的以**消费方证据**关闭，还是"注册 = 完成"？
- 闭环的最后一步是否总是留下可验证的痕迹？
- 是否存在"数据写入即完成"但下游从未读取的空转路径？
- 反馈回路的时延：从生产方产出到消费方消费，闭环时间多长？

## 审查方法

### 文件结构扫描

```
project/
├── CLAUDE.md           ← 使用指南还是 ADR？
├── lib/                ← 内核逻辑是否在此？
├── hooks/              ← 集成胶水是否在此？
├── scripts/            ← 工具脚本，职责单一？
├── commands/           ← CC commands，该用 hook 吗？
├── prompts/            ← agent prompt 是否清晰分层？
└── dev/                ← 开发工具/测试
```

### 调用关系编织

遍历所有 import / source / require 语句 → 绘制模块依赖图：
- 检测环形依赖
- 检测"枢纽模块"（被过多模块依赖，修改风险极高）
- 检测"孤立模块"（无人依赖但未被清理）

### 生命周期检查

对 hooks.json 中每个已注册 hook：
- 检查生产环境的 probe mtime 或触发日志
- 如果 mtime < 注册日期 = 从未触发
- 标记为僵尸架构

## 输出格式

每个发现：
```
[严重度] — 架构问题描述
  维度: <归属的审查维度>
  证据: <架构图 vs 实现 gap / 文件结构 / 调用关系>
  建议: <重构方向>
  验证: <一行命令, exit 0 = 已确认>
```

按严重度排序：P0 → P1 → P2。

最后给出**架构健康度评分**（1-10）：
- 10 分 = 概念自洽，架构与实现一致
- 扣分项：架构冗余、不遵循 CC 标准、内核胶水未分离、复杂度失控、反馈闭环不完整
- 附扣分明细
