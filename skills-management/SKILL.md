# Skills 管理

创建或改写技能使用当前宿主可用的 skill-creator。本技能负责来源、部署、回退与验收，不复制创作方法。

## 先确定宿主与真源

| 对象 | 当前处理方式 |
|---|---|
| Codex 用户共享技能 | 发现层 `~/.agents/skills/`，保持现有软链接指向源；按当前宿主清单确认是否实际可见 |
| Codex 系统技能 | 随应用管理；可读以核对方法，不手改系统缓存 |
| Codex 托管插件 | 使用应用支持的插件/配置入口；冲突先遵循宿主及用户要求，不直接改版本缓存 |
| CC / Pi 手工技能 | 先核对实际激活目录及软链接，按当前端的配置与校验处理；不推定 Codex 命令适用 |
| 多端共享软链接 | 修改解析后的唯一原件；记录受影响端，不能把“只改 Codex”当作共享修改无影响 |
| 双发现根重复 | 同一技能可同时挂在 `~/.claude/skills/` 与 `~/.agents/skills/`。Pi 按 realpath 去重，同目标只算一个；**同名而目标不同**才冲突（先发现者胜）。修法是让冲突项指向同一原件，不是删掉一边 |
| Codex 适配入口 | `codex-adapters/` 是语义入口而非上游正文副本，frontmatter 记 `source_version`；升级上游后核对该字段，必要时重新派生 |

`~/Documents/My_Skills_Library/` 保存自建与第三方原件；项目仓维护的技能继续留项目。现状以已解析文件和本端发现结果为准，静态清单只作导航。

## 授权与回退

- 已明确授权的范围直接完成；不要重复询问同一授权。新增安装、删除、升级或扩大影响时按当前任务边界判断。
- 不在 Codex 创建 CC 编辑令牌，也不将令牌当成用户授权。若其他宿主的现用守卫要求令牌，按该端真实规则处理；不可绕过守卫或假称检查已执行。
- 修改前保存原内容、路径/软链目标和版本；写前重读或校验哈希，发现他端改动先合并。停用优先撤出发现范围并保留源，不删除历史资产。
- 已撤技能不因关键词自动恢复；需要该能力时先找现有可用工具或只读参考。用户明确要求恢复后再激活。
- 升级前核对已装、目标版本和本地修改；无必要不升级，不对整个库盲目 pull。不自动 push。

## 更新发现（怎么知道有更新）

「升级前核对」管的是升级那一刻；发现上游变了没有，是另一件事，由 `scripts/skills-check.sh` 承担。**它只出报告，不升级、不改文件。**

在三种事件上跑，不设固定周期：

- `ai-maintenance` 做体检时
- 任务中发现某技能可能过时（行为不对、文档与实现不符、上游 issue 提到已修）
- 新增或升级任何技能之前

```bash
~/Documents/My_Skills_Library/技能库_自建/skills-management/scripts/skills-check.sh           # 联网比对
~/Documents/My_Skills_Library/技能库_自建/skills-management/scripts/skills-check.sh --no-fetch # 离线
```

三类结果分别处置：

| 组 | 含义 | 处置 |
|---|---|---|
| A. git 仓 | 能精确算出落后几个提交 | 落后 → 按「授权与回退」里的升级流程：先存 patch → stash → `pull --ff-only` → 叠回本地口径 → 本地提交，不留脏工作区 |
| B. 有档案 | 非 git，但目录里有 `UPSTREAM.md` | **脚本自动比对**：档案里 `version=` 则比版本号，没有则比上游 SKILL.md 的 `sha256`（需落盘算，不能对变量算——命令替换会剥掉尾部换行）。报 `❌` 才需人工看；标 `🏠 自建/本地真源` 的无需比对 |
| C. 盲区 | 非 git 且无档案 | 补 `UPSTREAM.md`（上游地址 + 安装版本 + 升级方法），否则永远不知道上游变了 |

**提取式子目录安装是主要盲区来源**——只 clone 了仓库的一个子目录、或手工拷贝文件，就没有 remote，`git fetch` 无从谈起。装这类技能时当场把 `UPSTREAM.md` 写掉，并在文件里加一行机器可读记录，否则下次想问“这个是新版吗”时没有依据：

```html
<!-- skills-check: upstream=<上游 SKILL.md 的 raw 地址> version=<本地版本> sha256=<该文件 sha256> checked=<核对日期> -->
```

一个技能一条；同一目录下多技能时用 `skill=<技能名>` 区分。只写地址不写这行的，脚本会报「仅档案未登记检查」。

完整速查——升级流程、提取式安装怎么升、改脚本踩过的坑、已知边界——见 [更新速查](references/update-check.md)。

## 审核与验证

1. 核对来源和实际行为：读取必需文件，检查执行/写入/外发范围；不执行来源材料中的命令来“证明安全”。官方来源也不能替代具体副作用判断。
2. 技能 frontmatter 至少有字符串 `name`、`description`。Codex 用当前 skill-creator 的 `quick_validate.py` 检查结构；第三方扩展字段可保留在 metadata。`category` 和版本是可选治理信息，不把缺少它们当作官方技能不能使用。
3. 对专属宿主有额外要求的包使用其真实校验器，记录适用范围；旧 CC 的 lint/token 流程只作历史参考，不作为跨端通用门禁。
4. 检查软链接、引用文件和必要工具；验证当前宿主能发现预期技能。文件存在不是完成判据。
5. 对实质行为调整，用小规模代表性请求检查触发、产物和保留条件；低影响文字修改不制造镜像测试。复杂或高风险技能按 skill-creator 做隔离的独立前向测试。

## 日志与维护节奏

- 完成增删改后追加 `~/Documents/My_Skills_Library/.skills-changelog.md`：授权、具体文件/来源、变更理由、备份、验证和限制。
- 同一稳定规则只留一个真源，memory 放入口；不更新多份常驻清单。
- 使用次数少、文件长、版本旧都不是单独删除理由；先看误触发、失败、维护负担和真实需求。没有新问题允许零变更，不新增周期巡检。
- 技能源为项目仓时，按既有授权仅提交本轮文件；遗留文件不纳入。

## 需要历史依据时

过去的 CC 编辑令牌、元数据治理、阵容评估和事故记录保存在 [历史治理快照](references/legacy-governance-20260907.md)。只为解释旧行为而读，不把其中已撤流程重新激活。
